### Stages

1. **Pickup** — The Implementer Agent picks up an approved Task with its Definition of Done, Acceptance Criteria, and risk markers.
2. **Risk Classifier** — Rules-based, deterministic. Examines the Task's touched paths against project-defined rules (e.g., changes under <Code>auth/</Code> are always Full Pipeline). Conservative by design: only escalates, never downgrades.
3. **Fast Lane / Full Pipeline** — Fast Lane: Implementer → Reviewer → Final Approval. Full Pipeline adds: UI Reviewer (if frontend touched), QA Agent (if functional tests warranted), Documenter Agent (always).
4. **Security Review** — Runs at the `automated-gates` hub in both lanes when a task's `security_class` is high. The Security Reviewer executes after code review and before merge/UI-review: a deterministic secret scan followed by an LLM vulnerability judgment. Blocker findings route to escalation; clean passes continue the lane.
5. **Final Approval Gate** *(Human)* — The single human gate in Delivery. Approves merge.
6. **Merge & Deploy** — The Implementer (or a deploy agent) merges and ships.

<Callout title="Why deterministic risk">
  AI is good at reasoning but bad at calibrating its own risk tolerance. Hard rules prevent an agent from talking itself into shipping a Fast Lane change that should have been Full Pipeline.
</Callout>

### Security-gate enforcement

The `security_gate` and `resets_security_verdict` annotations on the Task state machine constrain the existing delivery topology without adding new states.

- **`security_gate: true`** — annotates the three outbound edges from the `automated-gates` hub (`→ ui-review`, `→ qa`, `→ merged`). When a task's `security_class` is `"high"`, `advance-status` will refuse the transition with exit code 2 unless `security_review_verdict === "pass"`. The refusal is mechanical: the CLI re-runs `classify-security` on the actual diff before checking the verdict, so a task that was classified `low` at creation but touches sensitive paths in the real diff is caught at the gate.
- **`resets_security_verdict: true`** — annotates the `review → automated-gates` edge. When the Reviewer bounces a task back to the Implementer and rework is eventually re-submitted, the prior security pass is invalidated atomically with the status change. The Security Reviewer must run again before the guarded transitions are available.

These are preconditions on existing edges, not new states. The Security Reviewer still routes through `automated-gates` in both lanes.

### Failure handling on Delivery

- **Mechanical** (build break, test flakiness, lint) — auto-retry with the same agent.
- **Quality** (Reviewer rejection) — bounce once back to Implementer; if rejected again, escalate.
- **Strategic** (mid-implementation discovery that the Task is wrong) — escalate immediately to Discovery; the Task does not block the rest of the batch.
